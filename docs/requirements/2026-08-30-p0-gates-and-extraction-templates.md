## 1. 背景与问题

项目已完成 Excel 抽取与分析三阶段能力（上传预览 → 六工具抽取链路 → DuckDB 分析 + Generative UI），具备向真实用户演示的条件。但当前系统存在三个**阻断级缺陷**，任何一个都足以让对外交付失败：

1. **无用户隔离**：所有工件（上传文件、抽取脚本、结果 CSV）仅以 `thread_id` 隔离。任何人拿到 thread_id 或 artifact_id 即可访问他人数据，下载接口 `/api/files/{artifact_id}/download` 无鉴权（`SCAFFOLD_API_KEY` 仅为单 key 门禁）。
2. **沙箱裸奔**：LLM 生成的不可信 Python 代码以 subprocess 直接在宿主机执行，有 timeout/内存限制，但无文件系统与网络隔离。ADR-0001 明确这只是 Demo 期决策。
3. **稳定性缺口**：ModelRetry/ModelFallback/ToolRetry 中间件代码与测试已就绪，但在 `config.yaml` 中被整段注释。模型 429/超时即表现为 Agent 死亡。

同时，垂直场景存在最高频的体验损耗：**每个会话都要重新对齐抽取目标**（字段、类型、约束、示例行），而报价单类文件格式高度重复，该成本完全可以通过模板复用消除。

## 2. 目标与非目标

### 目标（本期验收即达成）

- G1：不同用户的数据（工件、会话、抽取任务）在 API 层完全隔离，未授权访问返回 401/403。
- G2：抽取脚本在隔离沙箱中执行，无法读写宿主机任意文件、无法访问内网。
- G3：单模型故障（429/5xx/超时）自动重试或回退，用户无感知；全链路失败给出可读错误。
- G4：同一用户再次上传同类文件时，可复用已保存的抽取模板，跳过目标对齐环节，一键完成抽取。

### 非目标（明确不做）

- 不做完整的企业级 RBAC / 组织架构权限，只做 user_id 级数据隔离。
- 不做多租户 SaaS 计费。
- 不做模板市场 / 跨用户模板共享（本期模板仅归属创建者）。
- 不引入新的文件类型（PDF/DOCX 抽取另行立项）。
- 不改造通道（飞书/Slack）侧权限，通道身份映射后续单独处理。

## 3. 需求详述

### R1 用户认证与数据隔离（对应 G1）

**用户故事**：作为部署方，我希望每个用户拥有独立身份，且只能访问自己的会话、工件与抽取任务，以便放心地把系统交给多人使用。

**需求要点**：

1. 引入 `user_id` 作为一级隔离维度，落库到 threads / artifacts / extraction_tasks 等所有会话数据表；现有 `thread_id` 作用域保持不变，作为 user 之下的二级维度。
2. 所有 API（含 `/agent*` SSE 端点、`/api/threads`、`/api/files/{id}/download`、`/api/agents`）在校验身份后必须校验资源归属：资源不属于当前用户 → 403；无身份 → 401。
3. 认证方式保持简单：在现有 `SCAFFOLD_API_KEY` 之上扩展为多用户 token 映射（配置驱动，如 `users: [{user_id, token}]`），不引入 OAuth/账号体系。
4. Agent 工具（preview_excel、generate_extraction_code 等六工具 + render_ui 的 download_button）在沙箱/仓储层同样按 user_id 过滤，防止 Agent 侧越权读取。
5. 存量数据迁移：无 user_id 的历史数据归属到保留用户（如 `legacy`），不删除。

**验收标准**：

- 用户 A 持有合法 token，请求用户 B 的 thread 消息 / artifact 下载 / extraction 查询，全部返回 403。
- 无 token 请求任何业务端点返回 401（`/health` 除外）。
- Agent 在 A 的会话中无法通过工具列出或读取 B 的工件。
- 存量数据迁移后，以 legacy 用户身份可正常访问。

### R2 生产级沙箱（对应 G2）

**用户故事**：作为部署方，我希望 AI 生成的抽取代码在与宿主机隔离的环境中运行，即使代码恶意或出错也不会影响服务器和其它用户数据。

**需求要点**：

1. 在现有 `infra/sandbox/factory.py` 上实现 docker provider（优先）或 e2b provider，二选一由 `execution_sandbox.provider` 配置驱动；subprocess 保留为本地开发默认。
2. 隔离底线：
   - 文件系统：仅挂载当前任务的工作区目录（只读输入 + 可写输出），不挂载宿主机其他路径。
   - 网络：默认禁网（抽取脚本无联网需求），如需开放须在配置中显式声明。
   - 资源：沿用现有 `timeout_seconds` / `memory_limit_mb`，容器级强制。
3. 工件流转通过 Artifact 仓储读写，不让沙箱直连数据库。
4. 沙箱启动失败、超时、OOM 均返回结构化错误，由 `execute_extraction_code` 转成可读信息给 Agent，不允许裸栈到用户。

**验收标准**：

- 脚本内尝试读取 `/etc/passwd`、访问 `https://example.com`、写入工作区外路径，三者均失败且返回结构化错误。
- 超过 memory_limit_mb 的脚本被终止并报 OOM 类错误；超过 timeout 被终止。
- `provider: subprocess` 时现有行为与测试全部保持通过（回归不破）。

### R3 韧性中间件启用（对应 G3）

**用户故事**：作为终端用户，模型供应商偶发限流或超时时，我不希望看到 Agent 直接死掉的错误页。

**需求要点**：

1. 默认启用 `ModelRetryMiddleware`（429/5xx/超时指数退避重试），参数沿用 config.yaml 注释中的建议值。
2. 配置 `ModelFallbackMiddleware`：主模型失败后回退到同配置内的备用模型；fallback_models 默认值写入 `config.yaml`（验证环境用 `config.verify.yaml` 的 mock 模型覆盖）。
3. `ToolRetryMiddleware` 默认启用但对幂等性未知的工具收敛为重试 1 次。
4. 所有重试与回退事件写入结构化日志（含 model、attempt、latency、最终成败），为后续成本看板留数据。

**验收标准**：

- mock 模型注入 429 → 首次失败后自动重试成功，用户侧无错误。
- 主模型持续失败 → 自动切到 fallback 模型完成响应，日志记录切换事件。
- 主备全失败 → 用户收到可读的「服务暂时不可用」而非栈信息。

### R4 抽取模板复用（对应 G4）

**用户故事**：作为货代/采购用户，我每周都会收到同一供应商同格式的报价单，我希望第一次对齐抽取目标后，后续同类文件直接套用，不再逐字段确认。

**需求要点**：

1. 新增「抽取模板」实体：归属 user_id，内容 = 验证通过的 Extraction Goal（字段、类型、约束、示例行）+ 对应 Extraction Script + 来源文件结构指纹（sheet 名、列头签名）。
2. 触发时机：某次抽取 `validate_extraction_result` 通过后，Agent 主动询问用户「是否保存为模板」；保存动作经由 Generative UI 按钮（button_group）确认，命名可编辑。
3. 复用路径：用户上传新文件时，Agent 先 `preview_excel` 取结构指纹，匹配到本用户模板（指纹相似 + 用户选择确认）→ 直接复用脚本执行 → 验证 → 出结果，跳过目标对齐。
4. 模板管理最小集：列出、重命名、删除（本期不做编辑字段级修改，修改=另存新模板）。
5. 模板经 `user_id` 严格隔离，不跨用户可见。
6. 指纹不匹配或复用脚本执行/验证失败 → 回退到完整六步流程，并提示用户模板可能已过期。

**验收标准**：

- 首次抽取成功 → 用户一键保存模板；第二次上传同格式文件 → 从上传到拿到验证通过结果，用户交互次数 ≤ 2 次（选模板 + 确认）。
- 上传列结构不同的文件 → 指纹不匹配，正常走完整流程，不强行套用。
- 模板列表/删除操作正确且他人不可见。
- 复用路径执行失败时自动回退完整流程并向用户说明原因。

## 4. 成功指标

| 指标 | 基线 | 目标 |
|------|------|------|
| 越权访问测试通过率 | 0%（无隔离） | 100% |
| 沙箱逃逸类测试（读敏感文件/联网/越界写）拦截率 | 0% | 100% |
| 注入单模型故障下的请求成功率 | 未度量 | ≥ 99%（重试+回退后） |
| 同类文件二次抽取的用户交互次数 | ~6-8 次（对齐+确认+迭代） | ≤ 2 次 |
| 同类文件二次抽取的端到端耗时 | 分钟级（多轮对话） | ≤ 首次的 30% |

## 5. 里程碑建议

| 里程碑 | 内容 | 依赖 |
|--------|------|------|
| M1 稳定性兜底 | R3 韧性中间件启用 | 无（代码已就绪，成本最低，先行） |
| M2 数据隔离 | R1 用户认证与隔离 | 涉及全部仓储层，改动面最大 |
| M3 沙箱隔离 | R2 docker provider | 与 M2 可并行；沙箱需感知工作区目录 |
| M4 模板复用 | R4 模板实体 + 复用流程 | 依赖 M2（模板归属 user_id） |

建议顺序 M1 → M2 → M3 → M4；M1 应在一周内完成，M2/M3 并行，M4 收尾形成「可对外演示的安全闭环」。

## 6. 风险与开放问题

1. **docker 依赖部署环境**：部分目标部署环境可能无 Docker。缓解：保留 subprocess 为开发默认，docker 不可用时启动告警降级而非拒绝服务——需评审是否接受该降级策略。
2. **指纹匹配的误配风险**：同供应商改一列即指纹不匹配，宁可多走完整流程也不套错模板（误判方向保守，已写入 R4 验收）。
3. **通道身份映射**：飞书/Slack 用户到 `user_id` 的映射本期不覆盖，通道接入前必须补齐，否则通道等于绕过隔离的侧门。
4. **存量数据迁移窗口**：R1 上线需要短暂停写或双写窗口，需在实施计划中明确。
5. **开放问题**：模板是否需要版本化（脚本随模型/库升级失效）？本期不做，观察复用失败率再定。
