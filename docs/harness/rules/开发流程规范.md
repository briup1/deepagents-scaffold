# 开发流程规范


## 1. 需求分析阶段
- 使用 `skills/需求分析/SKILL.md`：解析需求 → 业务/技术影响分析 → 冲突检测 → 输出分析文档。
- 产出经用户确认后才进入设计。

## 2. 技术方案设计
- 涉及新实体/接口/表结构时，先更新 `wiki/` 对应文件（或提出更新补丁），再动工。
- 跨前后端改动时，先确认接口契约（URL、方法、请求/响应体）。
- 方案要点：改哪些文件、怎么测、有什么风险。

## 3. 编码实现阶段
- 使用 `skills/编码实现/SKILL.md`，按 schemas(Pydantic) → repository → service/装配 → router（后端）/ API 封装 → 类型 → 组件（前端）顺序推进。
- **分支管理**：`main` 受保护；功能分支 `feat/<主题>`、修复分支 `fix/<主题>`，本地验证后合入。
- **提交规范**：按 `rules/工程结构.md` 第五节 Conventional Commits。
- **自检命令**（提交前必跑）：
  ```bash
  ruff check src tests && ruff format src tests   # 后端
  pytest                                          # 后端测试
  cd src/web && npm run build && npm test         # 前端
  ```

## 4. 代码评审阶段
- 提交前必过 `skills/代码审查/SKILL.md`（红线检查 + 性能与规范 + 坏味道）。
- 重大变更追加 `skills/专家评审/SKILL.md`（DDD 符合度、并发一致性、扩展性、技术债）。

## 5. 测试阶段
- 使用 `skills/单元测试编写/SKILL.md` 补测试。
- 覆盖率门槛 ❓（新提议，已获原则同意）：核心模块（`src/scaffold/api`、`src/scaffold/runtime`、`src/scaffold/infra`）行覆盖率 ≥ 60%；新功能必须带测试，无整体覆盖率门禁（当前 pytest/vitest 均未配覆盖率插件，接入时机由用户定）。
- **合入前反补检查（兜底）**：PR/提交说明必须勾选「已执行 harness-sync 反补（或本次无需反补）」；对照 `changes/` 检查是否有对应记录——无记录且未声明"无需反补"的，打回。这是防保鲜循环静默断裂的最低成本门禁。

## 6. 部署验证
- 使用 `skills/部署验证/SKILL.md`：健康检查 → API 冒烟 → 依赖验证 → 监控确认。
- 回滚策略 ❓（缺省决定）：无 CI/CD 部署环节，回滚 = `git revert` + 重启服务（`scripts/stop_dev.sh` 后 `scripts/dev.sh`）；数据库变更需配套回滚 SQL 或保持向后兼容的 `migrate()`。

## 7. 收尾（强制）
- 任务完成后执行 `harness-sync` 反补：新约定、新术语、协议/结构变更回流到本规范体系，并记录到 `changes/`。
